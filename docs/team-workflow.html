What connects them

git push / pull moves code between your computer and GitHub. The Linear connector lets your Claude Code read (and, when you ask, update) Linear. Putting ELL-10 in the branch name and PR title links GitHub and Linear.

Linear status of a task (target)

Backlog→ Ready→ In Progress→ Code Review→ Ready for QA→ Done

Still open: Elli sets these statuses up in Linear. Until then: Ready = Todo, Code Review = In Progress with the PR linked, Ready for QA = In Progress plus a comment.

Life of one task, from idea to main

This is the same path for everyone and for agents. Example: ELL-10 "Invite Travelers". Commands use Git Bash syntax; in Windows PowerShell 5.1, run each line on its own.

  1. ElliLinearBacklog → Ready

    The story is written and ready

    Elli turns an idea into a user story with acceptance criteria and puts it in a milestone. When it is clear enough to build, she moves it to Ready. Nothing is started before this.

  2. Whoever picks it upLinearLocalReady → In Progress

    Pick it up and start a branch

    Run the skill. It reads the issue, checks that your working tree is clean, updates main, creates the branch with the issue ID and sets the issue to In Progress.

    /start-task ELL-10

    Or by hand:

    git switch main && git pull git switch -c feat/ELL-10-invite-travelers
  3. You + your Claude CodeLocal

    Build it with your Claude Code

    Your Claude Code reads the issue from Linear, follows CLAUDE.md and docs/RULES.md (English, sensible comments, naming) and writes code and tests. Small commits, and only when you tell it to commit.

  4. YouGitHubIn Progress → Code Review

    Push and open a pull request

    Run /review-pr first to catch problems early. Then /open-pr pushes the branch, fills the template, puts the issue ID in the title (so Linear links it) and requests Marvin as reviewer.

    /review-pr /open-pr

    Or by hand:

    git push -u origin feat/ELL-10-invite-travelers gh pr create
  5. Marvincode-reviewerGitHub

    Security and quality review

    Marvin runs the code-reviewer agent (or /review-pr) on the branch and reviews the findings. Secrets, input validation, user data, new dependencies, tests. Marvin can veto a release over security findings. A Request changes review from Marvin blocks the merge until he resolves it.

  6. ElliEugenGitHubCode Review → Ready for QA

    Approval and squash merge

    Every PR needs approval from Elli or Eugen, never the author. The approver merges with squash into main after Marvin has reviewed, or after 48 hours without his response, then moves the issue to Ready for QA. One PR becomes one clean commit.

  7. MarvinElliLinearReady for QA → Done

    QA and Definition of Done

    The feature is tested against its acceptance criteria. If one fails, the issue goes back to In Progress. Agents never set Done. Done means: criteria met, reviewed, tests pass, no critical bugs, QA complete, docs updated, approved for release. Marvin leads QA, Elli gives the final acceptance.

  8. EveryoneLocal

    Everyone gets the new state

    On the next start of work, each person pulls main. Their Claude Code now knows the new code, and Linear shows the task as Done.

    git switch main && git pull

Your setup, once per person

Each of us does this one time. Afterwards, working on the project means opening your clone in Claude Code.

1 · Get access

  • Repo access: all three of us are already collaborators on the private repo.
  • Linear: all three of us are already members of the workspace.

2 · Install the tools

  • Git, the GitHub CLI and the Claude desktop app (Code tab).

Windows:

winget install GitHub.cli

macOS:

brew install gh

3 · Sign in to GitHub

The CLI shows a one-time code. You enter it in the browser while logged in to your own GitHub account.

gh auth login --web --git-protocol https

4 · Clone the repo

git clone https://github.com/ekutschkin-priv/travelApp.git

Open this folder as the project in Claude Code. It loads CLAUDE.md and the shared rules by itself.

5 · Connect Linear

The repo contains the Linear connection (.mcp.json). Claude Code asks you once to approve the project server; then sign in to Linear with /mcp. Do not add a second Linear connector in the app settings, because agents rely on the same tool names on every machine.

Check: ask your Claude "Which Linear issues are assigned to me?"

Good to know: Everybody signs in with their own account. Never share tokens or passwords, and never put them in the repo. Each Claude Code session only sees what its person may see.

Meeting up: how everyone sees what happened

We do not need a status report from each person. The state is already written down in three places. Everybody reads the same ones.

Linear board

What is going on

Status of every task, who owns it, which milestone it belongs to. Comments hold decisions and questions.

GitHub PRs and main

What changed

Open PRs show work in progress. The history of main shows one squashed commit per finished change.

Your Claude Code

The summary on demand

After a git pull, ask your Claude to catch you up. It reads the git log and Linear for you.

Ask your Claude"Summarize what changed on main since I last pulled, and which Linear issues moved."

When we sync

No fixed schedule

This is a hobby project. We meet ad hoc or whenever there is time, and Elli takes the lead: look at main together, walk the board, decide what moves to Ready next.

In between

Look at the board and open PRs when you start working, and git pull. Questions and blockers go into a Linear comment or the team chat.

When the rules need a change

Open a PR on docs/RULES.md or CLAUDE.md. It is reviewed like code, and after the merge every Claude Code follows the new rule.

How a story reaches an agent

  • A story with acceptance criteria sits in Ready in Linear.
  • A person runs /start-task ELL-10 in their Claude Code.
  • The session reads the issue through the project's Linear connection and works on a new branch.
  • It stops at the PR. Humans take it from there.

How it becomes visible to all

  • The PR shows the change to everyone on GitHub.
  • After the merge it is part of main.
  • Linear shows the new status and the linked PR.
  • Everybody's next git pull brings it to their machine.

Agents and skills at a glance

  • product-owner (Elli): story and acceptance criteria
  • code-reviewer (Marvin): security, backend, rules
  • ui-ux-reviewer (Elli): usability, accessibility, mobile
  • qa-tester (Marvin): test plan and QA checklist
  • /start-task, /review-pr, /open-pr: tie the steps together

All agents are read-only, run on a cheaper model and report in one findings format. Details in docs/AGENTS.md.

Ground rules for every agent

Never on mainAgents work on a branch and hand over through a PR.
Commit and push on requestOnly when a team member asks for it.
Linear: read freely, write on requestCreating or changing issues only when a person asks.
No secretsAgents never read, write or print tokens, passwords or .env files.
Never approve, merge or closeAgents do not approve or merge PRs and never set an issue to Done.
Ask when unsureDecisions belong to the role. Agents do not choose stack or paid services.
Same rules as humansEnglish, useful comments, naming convention.
Today's limit: agents run only while a person has a Claude Code session open. They do not watch Linear on their own and do not start work by themselves. Automation such as a bot that picks up Ready issues is a later step, and Eugen decides it with the team.
